# Parity matrix: the official SAP SDKs against the Go SDK

Acceptance test AT-011 of contract `sap-go-sdk`. One row per public feature of the four official packages, the Go
counterpart that will carry it, and (once written) the Go test that exercises it. A row with no counterpart is a
deviation for Randy to accept (contract section 8), never a silent gap: see "Deviations proposed" at the end.

## How to read the matrix

- Columns **TS client**, **Py client**, **TS agent**, **Py agent** show the upstream identifier that carries the
  feature, or `-` when that package has none. Where the cell would repeat the Feature column's identifier it shows
  `y`. The agent packages are the host side; the client packages are the caller side. Shared types (envelope, chunk,
  heartbeat payload) are exported by the client package and imported by the agent package, so the agent cells for
  those say `(client)`.
- **SAP section** is the protocol section the feature rests on, or `none` when it is outside the protocol.
- **Proposed Go counterpart** is the real identifier, `package.Identifier`, as `go doc` prints it (`docs/api-plan.md` is
  the original plan and `go doc` is authoritative; `docs/protocol-mapping.md` maps every identifier to its SAP section).
  Packages: `agents` (root), `caller`, `host`, `identity`, `tools`, `connect`, `agentstest`, `cmd/sapconform`.
  `connect` and `agentstest` are additions to the contract's package list. "not ported" names a deviation below.
- **Go test** names the tests that exercise the row, as `pkg.TestName` (`agents` is the root package; `test/caller` is
  the directory of the integration tests); a bare `TestName` continues the previous package. A row whose feature is not
  ported, or has no test of its own, says `none (D-n)` and cites its deviation. The AT-011 check
  (`test/docs/parity_test.go`) fails a row that names neither a test nor a D-id, a named test or exported identifier
  that does not exist, a D-id the deviations table lacks, and a deviation no row cites.
- **Notes** record behaviour differences between the TypeScript and Python packages, and every judgement that a
  feature is outside the protocol (marked **OUTSIDE**, with the reason). Marked **DEVIATION** rows are listed again
  at the end for Randy.

## Upstream quirks and what the Go SDK does

The official SDKs differ from each other in places the protocol leaves open. The Go SDK follows the protocol first,
and where it must choose it records the choice here.

| Quirk | Upstream | Go |
|---|---|---|
| Fractional `interval_s` | Python rejects a fractional `interval_s` (a status reply that carries one fails with status 500); TypeScript accepts it | Go reads and writes a float. A sub-second or fractional interval is opt-in (`host.WithSubSecondHeartbeats`), because a Python caller cannot read it (D-9) |
| Service errors | TypeScript keeps `{code, description, body}` in a `ServiceError`; Python flattens a service error to text in a `ProtocolError` and loses the code and body | Go keeps all three in `*agents.ServiceError` (`errors.As`, `agents.IsCode`) |
| Unsigned caller, signing required | A Python caller with no signer refuses locally before it publishes; a TypeScript caller publishes and gets 401 | Go refuses locally, before publishing, and the error matches `identity.ErrCannotSign` and `agents.ErrLocal` |
| `session` metadata | The Python host always advertises `session`; TypeScript only when set | Go advertises it only when set (`host.WithSession`); SAP §3.2 requires it only of a session-aware harness |
| Time units | TypeScript options and fields are milliseconds (`maxWaitMs`, `timeoutMs`); Python's are seconds (`max_wait_s`) | Go takes `time.Duration` everywhere; `interval_s` stays seconds on the wire |
